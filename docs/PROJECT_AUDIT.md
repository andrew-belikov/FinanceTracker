# Аудит зрелости проекта

Статус: актуальный рабочий документ

Дата среза: 2026-09-15

Проверенный commit: `fbe3984`

## Назначение

Этот документ фиксирует технические долги и улучшения, необходимые для
доведения FinanceTracker до устойчивого production-grade состояния. Проект
рассматривается как Docker-first система: штатными средами являются Docker
Compose и GitHub Actions, а отсутствие локального Python-окружения само по себе
не считается дефектом.

Приоритеты:

- `P0` — аварийный дефект, угрожающий данным, безопасности или доступности;
- `P1` — высокий риск, который следует закрыть до крупных функциональных работ;
- `P2` — системный долг, влияющий на поддержку, надёжность и развитие;
- `P3` — улучшение инженерной зрелости и публичного оформления.

## Резюме

На момент аудита дефекты уровня `P0` не обнаружены. Проект имеет рабочие
миграции, healthcheck-контракты, структурированные логи, hash-locked
зависимости, автоматический deploy по точному commit SHA и значимый набор
тестов. Основные риски сосредоточены в защите Docker build context,
недостаточной интеграционной проверке PostgreSQL, отсутствии формализованного
rollback при миграциях и архитектуре, выросшей из плоского layout небольшого
бота.

## P0 — аварийные дефекты

Активных пунктов нет.

Появление любого из следующих условий должно немедленно создать `P0`:

- потеря или необратимая порча финансовой истории;
- публикация токенов, ключей или клиентских данных;
- неконтролируемое выполнение торговых операций;
- невозможность восстановить production после штатного deploy;
- обход allowlist Telegram-бота.

## P1 — высокий приоритет

### P1-01. Защитить Docker build context

**Проблема.** Все образы используют корень репозитория как `build.context`, но
`.dockerignore` отсутствует. Локальный `.env` не копируется явной инструкцией
`COPY`, однако передаётся Docker builder вместе с остальным контекстом.

**Риск.** Секреты и локальные артефакты могут оказаться доступны сборщику,
увеличивают контекст и способны случайно попасть в будущий слой образа.

**Что сделать.**

- добавить строгий `.dockerignore`;
- исключить `.env`, `.git`, кэши, виртуальные окружения, тестовые артефакты,
  локальные данные и файлы IDE;
- исправить утверждение в `CONTRIBUTING.md` о передаче `.env`;
- добавить контрактный тест для обязательных исключений.

**Готово, когда.** В build context отсутствуют секреты и ненужные локальные
файлы, а CI проверяет ключевые правила `.dockerignore`.

### P1-02. Добавить реальный PostgreSQL integration job

**Проблема.** CI запускает unit-тесты, `compileall`, contract checks, secret
scan и `docker compose config`, но не поднимает PostgreSQL. При этом production
queries используют `DISTINCT ON`, `AT TIME ZONE`, `ON CONFLICT`, `FOR UPDATE`,
advisory locks и другие PostgreSQL-специфичные конструкции.

**Риск.** Ошибка SQL-диалекта, схемы, ограничения или миграции может пройти CI и
проявиться только при deploy.

**Что сделать.**

- поднимать PostgreSQL 16 в отдельном CI job;
- применять все миграции к чистой базе;
- проверять повторный идемпотентный запуск;
- выполнять минимальный набор реальных запросов bot, tracker и reporter;
- проверять обновление с предыдущего поддерживаемого состояния схемы;
- запускать `migrate --check` после применения миграций.

**Готово, когда.** Несовместимый SQL или schema drift блокируют merge до deploy.

### P1-03. Проверять сборку и запуск контейнеров до production

**Проблема.** Текущий CI валидирует Compose-конфигурацию, но не собирает образы
и не запускает стек. Полная сборка выполняется уже в deploy-контуре.

**Риск.** Ошибки Dockerfile, системных пакетов, entrypoint или runtime import
обнаруживаются слишком поздно.

**Что сделать.**

- собирать все first-party образы в CI;
- запускать минимальный Compose smoke test;
- проверять healthcheck и завершение `migrate`;
- по возможности передавать в deploy уже проверенные immutable images вместо
  повторной сборки на production runner.

**Готово, когда.** Deploy использует артефакты, которые уже были собраны и
проверены тем же CI run.

### P1-04. Формализовать backup и rollback миграций

**Проблема.** Deploy привязан к точному SHA и проверяет image identity, но перед
обновлением отсутствует обязательный подтверждённый backup и автоматический
rollback при частично успешном запуске.

**Риск.** Неудачная forward-миграция или несовместимый контейнер может оставить
production в состоянии, требующем ручного восстановления.

**Что сделать.**

- создавать проверяемый pre-deploy backup PostgreSQL;
- хранить source SHA, schema version и checksum рядом с backup;
- определить политику retention;
- сохранять предыдущие immutable image IDs;
- описать и автоматизировать допустимый rollback приложения;
- регулярно проводить restore drill на отдельной базе.

**Готово, когда.** Для каждого deploy существует проверенный путь восстановления
данных и предыдущей версии приложения с измеримым RPO/RTO.

### P1-05. Защитить ветку `main` и GitHub supply chain

**Проблема.** На дату аудита `main` не защищена, ruleset отсутствует, а
Dependabot alerts, code scanning и secret scanning не включены. Deploy
автоматически следует за успешным CI на `main`.

**Риск.** Ошибочный или скомпрометированный push получает короткий путь до
production.

**Что сделать.**

- запретить force-push и удаление `main`;
- сделать CI обязательной проверкой;
- включить GitHub secret scanning и Dependabot alerts;
- добавить Dependabot update configuration;
- добавить CodeQL;
- создать `SECURITY.md` и процесс реакции на уязвимости;
- закрепить используемые GitHub Actions по immutable SHA и регулярно их
  обновлять.

**Готово, когда.** Непроверенное изменение не может попасть в `main` или
production, а уязвимые зависимости автоматически обнаруживаются.

### P1-06. Удалить доказанный дублирующий и мёртвый код

**Проблема.** В `src/bot/services.py` сохранена старая реализация
`build_monthly_report_payload`, тогда как фактически используется реализация из
`src/bot/report_payload.py`. Также обнаружены кандидаты на неиспользуемые
reporting helpers и compatibility wrappers.

**Риск.** Исправления могут вноситься не в ту реализацию, а тесты и ревью будут
давать ложное ощущение покрытия.

**Что сделать.**

- подтвердить call graph для каждого кандидата;
- удалить старую реализацию monthly payload;
- удалить только доказанно недостижимые функции;
- сохранить compatibility wrapper лишь при наличии поддерживаемого caller или
  внешнего контракта;
- добавить тест, фиксирующий единственную каноническую точку формирования
  monthly payload.

**Готово, когда.** У каждой операции остаётся одна каноническая реализация, а
удалённый API не имеет поддерживаемых потребителей.

## P2 — системный технический долг

### P2-01. Перейти от flat layout к настоящему Python-пакету

**Проблема.** Dockerfile копируют содержимое `src/bot` и `src/tracker` прямо в
`/app`; код использует sibling imports, а тесты местами изменяют `sys.path`.

**Что сделать.** Создать единый installable package, перейти на абсолютные
импорты и оформить явные entrypoints. Миграцию выполнять поэтапно, без big-bang
переписывания поведения.

**Готово, когда.** Приложение и тесты импортируют одни и те же пакеты без
ручного изменения `sys.path` и зависимости от Docker copy layout.

### P2-02. Разделить крупные многоцелевые модули

Наиболее заметные концентрации ответственности:

- `src/bot/services.py` — бизнес-логика и orchestration;
- `src/bot/queries.py` — разнородный слой PostgreSQL-запросов;
- `src/tracker/app.py` — settings, ORM, API client, sync, persistence и startup;
- `src/bot/report_render.py` — HTML, представление и крупный renderer;
- `src/bot/jobs.py` — планирование и выполнение объёмных сценариев.

**Что сделать.** Выделять модули по реальным границам ответственности:
configuration, broker client, persistence, sync, read models, reporting,
notifications, handlers и jobs. Не вводить абстракции без конкретной смены
ответственности или зависимости.

**Готово, когда.** Entry points и handlers остаются тонкими, доменная логика
проверяется отдельно, а изменение одного отчёта не требует затрагивать общий
многоцелевой файл.

### P2-03. Изолировать reporting от Telegram bot

**Проблема.** Reporter image копирует весь `src/bot`, а `report_payload` зависит
от bot services, queries и runtime.

**Что сделать.** Выделить reporting package с явным входным контрактом,
отделить получение данных от построения payload и rendering, сократить состав
reporter image.

**Готово, когда.** Reporter не импортирует Telegram handlers/runtime и содержит
только необходимую отчётную логику.

### P2-04. Усилить контроль schema drift

**Проблема.** `migrate --check` проверяет ledger, checksum, pending migrations и
наличие таблиц, но не валидирует столбцы, типы, constraints и indexes. ORM и SQL
миграции частично выступают двумя источниками истины.

**Что сделать.** Выбрать каноническую модель схемы: перейти на полноценный
migration framework либо добавить декларативный schema manifest и строгую
проверку структуры PostgreSQL.

**Готово, когда.** Удалённый столбец, неверный тип, constraint или index
обнаруживаются автоматически.

### P2-05. Убрать устаревшие schema fallbacks

**Проблема.** Queries сохраняют optional-table fallbacks, несмотря на
обязательный startup migration. Такие ветки могут скрывать неполную или
повреждённую схему.

**Что сделать.** Зафиксировать минимально поддерживаемую schema version и
удалять fallback после завершения compatibility window.

**Готово, когда.** Неподдерживаемая схема приводит к явной ошибке readiness, а
не к молчаливому изменению финансовых расчётов.

### P2-06. Усилить безопасность контейнеров

**Проблема.** Python-образы запускаются от root; отсутствуют `read_only`,
`cap_drop`, `security_opt` и ограниченные writable paths. Базовые образы не
закреплены digest.

**Что сделать.**

- закрепить base images по digest;
- перевести bot, reporter и xray-client на non-root user;
- подготовить tracker к non-root startup, перенеся установку сертификатов в
  build stage;
- добавить read-only root filesystem и минимальные writable mounts;
- удалить build toolchain из runtime layer;
- проверить resource limits.

**Готово, когда.** Каждый контейнер работает с минимальными правами и
воспроизводимым базовым образом.

### P2-07. Добавить quality gates

**Проблема.** Нет единого `pyproject.toml`, lint, type checking, coverage gate,
Python security scan и проверок shell/Dockerfile.

**Что сделать.** Вводить проверки поэтапно: Ruff, coverage, типизация публичных
границ, затем Bandit или эквивалент, ShellCheck и Hadolint. Baseline не должен
маскировать новые нарушения.

**Готово, когда.** Новые ошибки стиля, типов, покрытия и небезопасные шаблоны
блокируют merge, не требуя одномоментного переписывания всего проекта.

### P2-08. Перейти на timezone-aware UTC

**Проблема.** ORM-модели используют deprecated `datetime.utcnow`, а CI уже
показывает соответствующие предупреждения.

**Что сделать.** Определить единый контракт времени, использовать timezone-aware
UTC и проверить сериализацию, PostgreSQL types и существующие данные.

**Готово, когда.** В production-коде нет naive UTC datetime, а тесты фиксируют
правила преобразования UTC и локальной зоны.

### P2-09. Упростить необязательную Ollama-инфраструктуру

**Проблема.** Внешняя сеть `localllm_localllm` требуется Compose ещё до запуска,
даже когда Ollama выключена.

**Что сделать.** Вынести Ollama connectivity в profile или override, сохранив
детерминированный fallback reporter.

**Готово, когда.** Базовый стек запускается без предварительного создания
ресурсов отключённой интеграции.

### P2-10. Актуализировать зависимости tracker

**Проблема.** `requirements/tracker.in` содержит `python-telegram-bot`, хотя в
tracker не найден соответствующий runtime import. В образ также устанавливаются
`build-essential` и `libpq-dev`, несмотря на использование binary wheel.

**Что сделать.** Подтвердить dependency graph, удалить неиспользуемые прямые
зависимости и применить multi-stage build, если компиляция действительно нужна.

**Готово, когда.** Каждый runtime image содержит только используемые библиотеки
и системные пакеты.

### P2-11. Привести документацию к единому источнику истины

**Проблема.** `ARCHITECTURE.md` не описывает полный стек и trust boundaries;
`CONFIG.md` содержит формулировки про ранние PR; `BEHAVIOR.md` не охватывает
часть актуальных команд; roadmap и старые review-файлы выглядят как действующие
документы; встречаются абсолютные локальные ссылки.

**Что сделать.**

- переписать `ARCHITECTURE.md` по фактическому Compose и deployment topology;
- синхронизировать `BEHAVIOR.md` с командами бота;
- удалить устаревшие формулировки из `CONFIG.md`;
- перенести завершённые планы и аудиты в `docs/archive/` с явным статусом;
- заменить абсолютные ссылки относительными;
- добавить индекс действующей и исторической документации.

**Готово, когда.** Каждый актуальный контракт описан ровно в одном месте, а
исторические документы невозможно принять за руководство к действию.

## P3 — инженерная и проектная зрелость

### P3-01. Ввести управляемую release-модель

`CHANGELOG.md` отстаёт от фактического развития, а версии не закреплены Git tags
и GitHub Releases.

Нужно определить формат версий, правила changelog, создавать annotated tags и
релизы из проверенного commit SHA.

### P3-02. Определить лицензионный статус

Публичный репозиторий не содержит `LICENSE`. Следует либо добавить выбранную
лицензию, либо явно указать proprietary/all-rights-reserved статус. Выбор
лицензии является решением владельца и не должен угадываться автоматически.

### P3-03. Заполнить метаданные GitHub

Добавить краткое описание, topics и при необходимости homepage. Они должны
соответствовать фактическому назначению self-hosted read-only portfolio tracker.

### P3-04. Формализовать эксплуатационные цели

Определить SLO для freshness снапшотов и доставки уведомлений, допустимую
задержку T-Invest API, RPO/RTO, правила alerting и периодичность restore drill.

### P3-05. Добавить архитектурные решения

Зафиксировать ADR для ключевых решений: Docker-first execution, PostgreSQL как
источник истины, forward-only migrations, изоляция proxy, граница reporter и
политика времени. ADR должны объяснять причины и последствия, а не дублировать
инструкции запуска.

### P3-06. Контролировать размер и сложность новых изменений

Добавить мягкие метрики сложности и размера модулей без требования немедленно
переписать legacy-код. Новые изменения не должны увеличивать уже существующие
многоцелевые модули без обоснованного плана выделения ответственности.

## Общие критерии завершения аудита

Аудит можно считать полностью закрытым, когда:

- в Docker build context не передаются секреты;
- CI проверяет реальный PostgreSQL и собирает runnable images;
- deploy имеет проверенный backup/rollback path;
- `main` и supply chain защищены обязательными проверками;
- production-код оформлен как пакет с явными архитектурными границами;
- дублирующий и неподдерживаемый compatibility-код удалён;
- контейнеры работают с минимальными правами;
- schema drift, lint, типы и покрытие контролируются автоматически;
- актуальная документация отделена от архива;
- лицензия, версии, релизы и эксплуатационные цели определены.

## Ограничения среза

Это аудит репозитория и GitHub-контура, а не подтверждение текущего состояния
production-контейнеров или целостности production database. Исторические
результаты ручных проверок не считаются текущей operational acceptance без
повторной live-проверки.
