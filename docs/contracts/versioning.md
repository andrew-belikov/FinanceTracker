# Совместимость и версионирование

- **Contract ID:** `contract_policy.v1`
- **Статус:** active
- **Владелец:** maintainers FinanceTracker
- **Producer / consumers:** все компоненты, изменяющие или использующие
  долговечные контракты
- **Источник проверки:** contract tests, migration checks, JSON Schema и OpenAPI

## Формат версий

Идентификатор wire/data-контракта имеет вид `<name>.v<major>`. Major меняется
только при несовместимом изменении. Git-коммит и release tag обеспечивают
точную ревизию внутри major-версии; они не заменяют версию контракта.

`schema_manifest.v2` — версия ожидаемой структуры PostgreSQL, а не версия
данных пользователя. Последовательность применённых миграций и их SHA-256
дополнительно входит в digest manifest.

## Классы изменений

| Изменение | В той же major-версии | Требование |
|---|---|---|
| Добавить необязательное поле ответа/payload | да | consumer MUST игнорировать неизвестные поля |
| Добавить необязательное поле запроса | да | producer сохраняет прежнее поведение при отсутствии поля |
| Расширить набор error code / enum | да, с осторожностью | consumer MUST иметь безопасный fallback |
| Сделать необязательное поле обязательным | нет | новая major-версия |
| Удалить или переименовать поле | нет | новая major-версия и миграция consumers |
| Изменить тип, единицу, знак, timezone или смысл поля | нет | новая major-версия |
| Изменить authentication boundary | нет | security review и новая major-версия |
| Добавить nullable DB column/index/table | да | forward-only migration перед новым runtime |
| Удалить/переименовать DB object или сузить тип | нет для rolling deploy | staged migration и доказанная совместимость |

Машиночитаемые схемы фиксируют обязательное ядро текущей major-версии и
разрешают дополнительные поля. Producer MUST обновлять схему при добавлении
известного поля, даже если старые consumers уже совместимы с ним.

## Правила rollout

Для wire/payload-контрактов применяется порядок **expand → migrate consumers →
contract**. Новая версия публикуется до переключения producer; старая версия
сохраняется, пока все consumers не переведены или не существует проверенный
совместимый adapter.

Для PostgreSQL:

1. применить additive forward migration;
2. развернуть runtime, способный работать с обеими формами;
3. выполнить backfill с измеримым критерием завершения;
4. переключить readers/writers;
5. destructive cleanup вынести в отдельную явно одобренную migration.

Откат приложения MUST NOT требовать отката уже применённой migration.
Rollback-файл, если он хранится для аварийной процедуры, не входит в обычный
автоматический migration path.

## Deprecation

Deprecated contract обязан иметь owner, replacement, дату/условие удаления и
способ наблюдать оставшихся consumers. Историческое происхождение не является
основанием сохранять контракт без активного consumer. View `deposits` —
временный compatibility layer; активный runtime читает `operations`.

## Failure semantics

Неизвестная версия, отсутствие обязательного поля, нарушение типа или DB drift
MUST завершаться явной ошибкой до частичной записи или выдачи артефакта.
Fallback допустим только если он документирован в конкретном контракте и не
скрывает потерю данных, смешение валют или ослабление authentication.

## Критерий готовности изменения

Изменение контракта готово, когда спецификация, producer, все in-repo consumers,
fixtures/contract tests, migration/rollout note и failure-path проверены одной
ревизией. Локальный unit test одного producer не доказывает совместимость всей
границы.
